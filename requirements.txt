# NovelForge - AI 长篇网文创作工作流需求文档

## 1. Core Features (核心功能)

本系统旨在辅助网文创作者完成从灵感到完本的全流程，特别针对 1-100 章长篇幅的逻辑连贯性和文笔风格进行优化。

### 1.1 灵感架构师 (The Architect) - Idea to Outline

将用户的简短灵感扩展为结构严谨的百章大纲。

* **世界观构建**：根据一句话灵感，自动生成力量体系、地理势力分布、核心矛盾。
* **分卷规划**：将 100 章拆解为 4-5 卷，定义每一卷的主题（Theme）和高潮点（Climax）。
* **节奏控制**：自动在第 3、10、30 章等关键节点设置爽点或转折，生成包含 100 个章节标题和简要剧情的列表。

### 1.2 智能编辑 (The Editor) - Outline Refinement

对已有的粗糙大纲进行深度润色和逻辑修复。

* **逻辑自洽检查**：识别大纲中的逻辑漏洞（如：主角在第 20 章已死，第 30 章又出现）。
* **剧情冲突增强**：检测平淡章节，自动插入反派挑衅、宝物出世等网文经典冲突桥段。
* **结构优化**：调整故事节奏，确保“黄金三章”具有足够的吸引力。

### 1.3 风格变色龙 (The Mimic) - Style Transfer

基于参考小说进行风格化的仿写。

* **风格提取**：分析上传的小说样本，提取用词习惯（古风/白话）、句式结构（短句/长句）、叙事视角。
* **风格迁移**：将一段平铺直叙的文字，重写为目标风格（例如：将“他生气了”重写为土豆风的“恐怖如斯”或猫腻风的“甚至有些许恼火”）。
* **RAG 辅助**：建立风格向量库，在生成时检索相似的描写片段作为参考。

### 1.4 深度代笔 (The Ghostwriter) - Outline to Full Novel

将章节大纲扩写为 3000-5000 字的高质量正文。

* **分镜拆解 (Beat Sheet)**：将 200 字的章纲自动拆解为 6-8 个具体的场景分镜，每个分镜 500-800 字。
* **流式扩写**：逐个分镜生成正文，保持场景间的平滑过渡。
* **长时记忆 (Long-term Memory)**：利用 Redis 维护“滑动上下文窗口”，确保第 80 章能记得第 1 章的伏笔，角色名字和物品状态不混淆。

## 2. User Stories (用户故事)

* **As a 网文新手 (Newbie Writer)**
* I want 输入“一个程序员穿越到赛博朋克世界修仙”这个简单想法，
* So that 系统能直接给我吐出一份 100 章的详细大纲，让我知道每章该写什么。


* **As a 资深作者 (Pro Author)**
* I want 上传我自己写的一份粗略大纲，并告诉系统“增加悬疑感”，
* So that 系统能帮我把流水账大纲修改成跌宕起伏的剧情线。


* **As a 同人作者 (Fanfiction Writer)**
* I want 上传 10 章《诡秘之主》的内容作为样本，
* So that 系统生成的文字能带有“克苏鲁”和“英伦风”的味道，读起来像原著。


* **As a 工作室写手 (Ghostwriter)**
* I want 点击“开始写作”，系统就能根据大纲自动把第 1-100 章全部写完，且每章都在 3000 字以上，
* So that 我只需要进行简单的校对和修改就能交稿。


* **As a 剧情策划 (Plot Planner)**
* I want 系统在写到第 50 章时，依然记得主角在第 5 章获得的一把断剑，
* So that 故事的前后逻辑是连贯的，不会出现“吃书”现象。

## 3. Acceptance Criteria (验收标准)

### 功能 1：Idea -> 大纲

* [ ] **完整性**：输出必须包含世界观设定、主角人设、以及 1-100 章的完整章节列表。
* [ ] **结构化**：大纲必须按卷（Volume）划分，且每卷有明确的开始和结束节点。
* [ ] **响应时间**：从输入 Idea 到生成完整大纲，总耗时不超过 60 秒。

### 功能 2：大纲润色

* [ ] **逻辑修复**：如果输入的大纲包含明显逻辑错误（如死人复活），系统必须在润色版中修复或标记出来。
* [ ] **指令遵循**：若用户要求“加快节奏”，生成的新大纲必须减少日常对话，增加冲突事件的密度。

### 功能 3：仿写

* [ ] **风格相似度**：经人工或 NLP 评估，仿写段落的用词重合度与目标风格需达到高相关性。
* [ ] **内容准确性**：仿写后的内容必须保留原剧情的核心信息，不能因为追求风格而丢失剧情。

### 功能 4：正文生成

* [ ] **字数达标**：生成的每一章正文去除空格后，字数必须在 3000-5000 字之间。
* [ ] **记忆保持**：在第 90 章提及主角姓名、功法等级时，必须与第 1 章设定一致。
* [ ] **无重复循环**：正文中不得出现大段重复的废话或死循环文本。
* [ ] **格式规范**：输出文本需包含正确的段落缩进和对话引号。

## 4. Non-functional Requirements (非功能性需求)

### 4.1 性能与稳定性

* **并发生成**：系统需支持后台队列生成（Queue），用户点击生成 100 章后，即使关闭浏览器，任务也应在后台继续执行。
* **状态持久化**：所有生成过程中的中间状态（如写到第几章、当前的大纲版本）必须实时存入 Redis/Database，防止意外中断导致进度丢失。

### 4.2 模型与成本

* **长窗口支持**：核心生成模块必须使用支持至少 32k Context Window 的模型（如 Doubao-Pro-128k），以保证连贯性。
* **Token 优化**：在进行“分镜扩写”等非逻辑核心任务时，应优先使用低成本模型（Doubao-Lite）以控制 API 成本。

### 4.3 扩展性

* **模块化设计**：风格库、大纲模板库应设计为插件式，方便后续增加新的流派（如“末世文”、“系统文”）。
* **数据导出**：支持将生成的小说一键导出为 TXT、Markdown 或 EPUB 格式。

### 4.4 隐私与安全

* **内容合规**：接入火山引擎或其他服务商的内容安全接口，确保生成的网文不包含违禁内容（涉黄、涉政等）。
* **数据隔离**：不同用户的小说设定和生成内容必须严格隔离，禁止数据混淆。
